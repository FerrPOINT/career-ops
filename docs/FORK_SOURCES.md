# Региональные источники и происхождение дополнений

Проверено 2026-11-03. Это дополнения FerrPOINT к career-ops 1.38.0,
база `20b9fd3a9c86d28c847e021f4dbbe93ce9a39a00`.

## Переносимые возможности

| Источник | Провайдер | Доступ и ограничения |
| --- | --- | --- |
| Хабр Карьера | `habr-career` | Публичный HTML, страницы по дате; подтверждённый remote отдельно от города; дата публикации |
| GeekJob | `geekjob` | Публичный `/vacancies`, пагинация по пути; remote только по метке карточки; дата требует ручной проверки |
| DOU | `dou` | Публичный RSS, окно последних 25 публикаций; это не полный каталог |
| Djinni | `djinni` | Публичный RSS, ограниченное окно; компания/география доступны при ограниченном opt-in чтении JSON-LD карточек |
| HeadHunter и региональные сайты группы | `hh` | Только официальный API; на этой машине ответил 403. Выключен в примере; HTML fallback отсутствует |
| GetMatch | `getmatch` | Публичный HTML; текущая страница отдаёт JS shell без карточек. Это ошибка доступности, а не пустая выдача; выключен в примере |

Все провайдеры работают через существующий `providers/_registry.mjs` и общий
HTTP-транспорт с лимитом ответа, timeout, DNS/IP guard и запретом автоматических
редиректов. Пагинируемые источники ограничены числом страниц, используют общие
retry/pacing helpers; 403 не ретраится. Один провайдер не пишет файлы и не
создаёт второй трекер. URL отдельных публикаций участвуют в дедупликации;
разные ID вакансий с одинаковым заголовком не должны склеиваться.

Настройки — [portals.ru-cis.example.yml](../config/portals.ru-cis.example.yml).
Это пример поиска, не профиль кандидата. Его можно передать существующему
сканеру через `CAREER_OPS_PORTALS` или перенести выбранные записи в `portals.yml`.
Одинаковая компания на разных площадках не доказывает одинаковую вакансию.

  общими retry/pacing helpers и provider-local настройкой enrichment.
- [aleksnick93/career-ops-ru](https://github.com/aleksnick93/career-ops-ru):
  изучены региональные сценарии. Старый HTML-сканер hh.ru, собственный YAML
  parser и налоговые таблицы не переносились. СНГ-сайты у донора в основном
  заданы поисковыми запросами, а не адаптерами.
- [SWDevStudio/otklik-kit](https://github.com/SWDevStudio/otklik-kit):
  изучен подход к нескольким резюме. Код Bun/Chrome и автоматическое создание

## Доступ и source policy

`robots.txt` проверены для конкретных путей, с User-agent `career-ops`.
На дату проверки Хабр `/vacancies`, GetMatch `/vacancies`, GeekJob `/vacancies`,
DOU `/vacancies/feeds/`, Djinni `/jobs/rss/` не запрещены.

Поиск `hh.ru/search/vacancy` запрещён для автоматического обхода. Поэтому его
донорский HTML-сканер не включён. У `api.hh.ru/robots.txt` — 404; официальная
[документация API](https://api.hh.ru/openapi/redoc) описывает поиск вакансий
и рынки `hh.ru`, `hh.kz`, `hh.uz`, `rabota.by`, `hh1.az`, `headhunter.ge`,
`headhunter.kg`. Адаптер читает только этот API и не пытается обходить отказ.
Рынок API выбирается `hh.site`; это не разрешение на работу в стране.

`opendata.trudvsem.ru/robots.txt` запрещает обход всех путей. Донорский адаптер
«Работы России» оставлен вне исполняемого набора до разрешения вопроса доступа.
GetMatch `/api/` также запрещён; JS shell не повод переключаться на него.
Требования источников могут меняться: перед регулярным сканированием проверить
их повторно. Не менять аккаунты, User-Agent или сеть ради обхода ограничений.

## Проверка и честные пределы

Живые запросы через общий транспорт дали на первой странице: Хабр Java remote —
25 карточек с работодателями и датами; GeekJob — 20 с работодателями;
DOU Java — 25 с работодателями и датами; Djinni Java — 77 с датами, без компании
в RSS. Это проверка парсинга и доступа, не подтверждение пригодности вакансий.
Хабр-карточки с модификатором `vacancy-card--bp` учитываются наравне с обычными.

Автотесты проверяют контракт registry, разбор кириллицы/entities, remote/onsite,
пагинацию, ограничения probe, недоступную страницу вместо ложного нуля,
ошибки API, RSS envelope, enrichment и разные posting ID.

Интеграционный `scan.mjs --dry-run --json` в отдельном временном data root
прочитал Хабр и GeekJob: 44 карточки после provider-level remote-фильтров,
37 отсеяны общим фильтром заголовков, 7 предложены в очередь, ошибок нет.
`dry_run: true`: pipeline, tracker и scan-history не создавались. Это диагностика
источников без кандидатского профиля и без оценки соответствия человеку.

Даты без года/времени и отсутствующая география не достраиваются догадками.
У GeekJob публикация не имеет машинной даты в списке: `max_posting_age_days`
не доказывает свежесть такой строки. У Djinni без enrichment неизвестны
работодатель и место. Полная оценка и действие требуют проверки исходной
вакансии. Проверки фактов резюме не заменяются ключевыми словами вакансии.
