# Поиск работы: рабочий процесс нашего форка

## Назначение

Один поиск → одна очередь `data/pipeline.md` → оценка → выбор резюме →
проверенный отклик → результат в `data/applications.md`.
Документы и отчёты помогают принять решение; отправленный отклик подтверждается
только фактическим действием на площадке.

## Объём интеграции

- Перенести полезные источники в существующий контракт `providers/`.
- Сохранить общий сканер, фильтры, дедупликацию и трекер.
- Добавить примеры настройки под Java/backend, архитектуру, fullstack и agentic.
- Добавить выбор направления резюме без выдуманных фактов и изменения исходного CV.
- Проверить парсеры, ошибки доступа, пагинацию и реальную выдачу разрешённых источников.
- Сохранить происхождение кода и лицензии; доставить изменения в наш GitHub-форк.

Второй веб-сервер, отдельная БД, автоматическая отправка откликов, AdsPower,
чужие персональные профили и налоговые таблицы из старых форков для этого не нужны.
Существующий CLI уже владеет очередью, трекером и генерацией документов.

## Источники истины

Опыт и тексты резюме сверяем с текущими страницами hh.ru. Старые документы
используем как исторический контекст, не как доказательство текущего состояния.
В `cv.md` попадают только проверенные факты. Варианты резюме сохраняют полную
базу работодателей, должностей и дат; меняются акценты и формулировки.
Персональные файлы, контакты, переписка и cookies в Git не попадают.

## Рабочий цикл

1. Проверить профиль: `node doctor.mjs --json`.
2. Проверить текущие резюме на hh.ru через встроенный браузер Codex; выбрать
   подтверждённые факты для локального `cv.md`. Не импортировать старые выгрузки
   автоматически.
3. Настроить `config/profile.yml`, `modes/_profile.md`, `modes/_brief.md`:
   русский язык, удалённая работа, целевые роли и подтверждённые ограничения.
   Зарплатные ожидания и требования к английскому актуализировать отдельно.
4. Настроить `portals.yml` по примеру региональных источников. Сначала выполнить
   `node scan.mjs --dry-run --json`, затем обычный скан после проверки выдачи.
5. Оценить короткий список: требования → подтверждённый опыт → пробелы →
   выбранное резюме → минимальные правки → черновик письма.
6. Сверить вакансию и резюме во встроенном браузере. Показать точный текст
   изменений. Сохранение на hh.ru и отправка требуют отдельного подтверждения
   непосредственно перед действием. Shared workplace controls проверять
   по правилам родительского HH Resume Workbench.
7. Только после фактической отправки ставить `Applied`. Для существующей строки:
   `node set-status.mjs --report N Applied`.
8. Записывать ответы и этапы интервью. Анализировать `stats`, `patterns`,
   `calibrate`; не считать отсутствие ответа доказательством причины отказа.

## Проверка на небольшой выборке

Начать с 1–2 свежих вакансий на каждое направление одновременно: Java/backend,
архитектура/Tech Lead, fullstack, agentic/LLMOps, hands-on CTO/Head,
Go-переход. Это выбранный пользователем режим старта, не утверждение об опыте
в каждой технологии или о прошлом названии должности. Для каждой показать
ссылку, дату, формат, зарплату (или «не указана»), требования, пробелы,
рекомендуемое резюме и следующий шаг. Оценку модели считать рекомендацией.
Сравнить трудозатраты и результаты, прежде чем включать расписание.

## Обновление форка

Дополнения в `providers/`, тестах и документации — код нашего форка.
Обновлять его через Git с просмотром diff и проверками. Встроенный
`update-system.mjs apply` устанавливает системные файлы upstream; не использовать
его как способ слияния форка. Персонализацию хранить в пользовательском слое.

## Текущие внешние ограничения

Доступность источника и корректность парсера проверяются отдельно. HTTP 403,
CAPTCHA, логин или запрет обхода не означают «вакансий нет» и не обходятся
сменой аккаунта, прокси или браузера. Для hh.ru сохраняется ручная работа через
встроенный браузер Codex и загрузка предоставленного текста вакансии.

Сведения о переносимом коде и проверках источников — в
[FORK_SOURCES.md](FORK_SOURCES.md).

## Команды первого знакомства

В локальном пользовательском слое уже подготовлены русский язык, шесть
направлений, source config и таблица направлений резюме. Эти файлы исключены из
Git. `doctor` пока сообщает отсутствующий `cv.md`: персональные оценки и
черновики откликов начинаются после сверки текущего резюме и подтверждения
фактов. Не создавать CV из шаблонного кандидата ради прохождения проверки.

Из корня checkout в PowerShell:

```powershell
npm install --ignore-scripts --package-lock=false
node doctor.mjs --json
node resume-route.mjs --help
```

Зависимости установлены без postinstall: Chromium для PDF на этом шаге не нужен.
Проверка doctor не создаёт профиль.

На Windows после обычного `git clone` ссылки других CLI могут оказаться
текстовыми заглушками. Для их штатного раскрытия перед полной проверкой:

```powershell
node --input-type=module -e 'import { materializeSkillEntrypoints } from "./scaffolder/bin/skill-entrypoints.mjs"; console.log(materializeSkillEntrypoints(process.cwd()));'
```

Helper меняет только известные link-заглушки на канонический skill. Git на такой
машине покажет шесть локально изменённых alias-файлов; в коммиты форка эти копии
не включать. Канонический `.agents/skills/career-ops/SKILL.md` не меняется.
Для Codex используется именно канонический skill.

После подтверждения профиля и резюме:

```powershell
Copy-Item config/resume-routes.example.yml config/resume-routes.yml
# Сначала проверьте labels/signals под актуальные варианты резюме.
node resume-route.mjs --jd jds/example.txt

$env:CAREER_OPS_PORTALS = (Resolve-Path config/portals.ru-cis.example.yml).Path
node scan.mjs --dry-run --json
Remove-Item Env:CAREER_OPS_PORTALS
```

`jds/example.txt` — сохранённый текст выбранной вакансии, который надо подготовить
до команды. `resume-route` читает только локальный текст и YAML; не скачивает
страницы, не переписывает резюме и не отправляет отклик. Несколько направлений
в выдаче означают необходимость осознанного выбора основного и запасного резюме.
